# 前置上下文与实际模型输入

这份附件解释三条开发链“为什么这样做、模型实际收到了什么约束”。它补充已有完整 Prompt 链之前或之外的来源，**不扩展、不改写三条完整链的边界**。用户的“继续推进吧”“继续做”都是实际续办指令；较具体的技术约束来自此前交付的设计、计划、交接记录及 Codex 工具输入。

## 如何区分角色

| 标记 | 本附件中的含义 | 不能据此声称什么 |
| --- | --- | --- |
| 用户目标／原话 | 原记录中用户实际说过的话 | 不把助手补充的架构、测试或提示词写成用户逐字要求 |
| 批准上下文 | 用户在获知产品及计划后授权开始、继续；技术细节仍标明为 Codex 提议 | 不表示用户逐条写出、逐句批准过所有技术选择 |
| Codex 派发约束 | Codex 为独立审查准备并由审查模型实际读取的材料 | 不冒充真人写给 AI 的 Prompt |
| 工具提示／模型上下文 | 实际发给图像工具的 prompt，或保存的应用模型 `context`、`raw` 和 `reply` | 不把图像概念稿当计算依据，不把应用正文全部当模型自由生成 |

所有时间均为 UTC；“主记录”“Task 2 审查记录”“Task 3 审查记录”是不同来源，各自行号从 1 起算。逐条原记录 SHA-256、附件校验值和转换说明在 [上下文来源索引](context-manifest.json)。附件只收录明确指定的消息或段落，未宣称覆盖这些前置轮次的全部对话。

## 链 1：真实运行页面 → 读数修复

主记录第 893 行在数值引擎完成后明确推荐“运行API＋最小波形页面”：输入频率和采样率，显示原信号、采样点、频谱、重建曲线及警告；第 900 行用户回复“继续推进吧”。这使 [Task 2 完整链](task2-prompt-chain.md)中的续办指令有了可核对的具体对象。

当时的计划 Task 2 已约束：SQLite 保存真实运行；参考线、采样点、频谱和重建曲线使用同一运行结果；先发 A 后发 B、B 先完成时最终仍显示 B 的 `run_id`；在浏览器核对轴单位、边界说明和同步。这些是批准计划内的助手技术方案，不是给用户追加的引号原话。

实际模型输入有两种，分别证明界面意图和审查重点：

- [图像工具完整 prompt](context/task2-imagegen-prompt.txt)：逐字抽自主记录第 947 行 `const prompt`，与项目 `docs/design/concept-generation.md` 的记录完全一致。原文明确写了 `Do not invent accuracy or learning-effect numbers.` 及 `this generated image is only the design reference.`。这是 Codex 发给图像工具的提示，生成图只作为布局参考，真实数组及 UUID 由应用生成。
- [Task 2 审查模型实际读取的输入](context/task2-review-input.txt)：审查记录第 14 行请求读取审查包，第 16 行返回其内容。包中原文包括 `request races, result ownership, scientific plot accuracy at Nyquist/DC and odd sampling rates`，并限定只读审查、保留构建警告、区分实际发现与未测建议。已与当时保存的审查包核对，唯一文字脱敏是工作目录。

Task 2 审查记录第 73 行发现 `5/49` 运行主峰为 `5.000000000000001`，建议只格式化界面且保留 JSON 原值；主记录第 1448 行承接该问题。随后两条显示测试先失败，`fe74ade` 修复显示函数，前端六项通过，`5/49` 和 `54/49` 的真实运行都显示 5 Hz。详细 [RED、GREEN 与浏览器记录](task2-ui.md)和完整链维持原样。

## 链 2：可还原的学习记录 → CSV 上下文与超时修复

主记录第 1522 行向用户建议下一步“先预测→运行实验→迁移题→保存学习记录”；第 1529 行用户要求“你做好记录，明天接着做”；第 1571 行 Codex 明确接续为“Task 3：学习记录与服务端判题”。[交接记录](context/handoff-2026-11-04.txt)来自 `86558bf`，工作目录已脱敏。第 1590 行的“继续做”承接这份具体交接，随后开始 [Task 3 完整链](task3-prompt-chain.md)。

实际读取记录：主记录第 1594 行调用工具读交接，第 1600 行读取设计接口和 Task 3 计划；独立审查记录第 14、16 行又分别请求并收到计划。[审查模型实际收到的 Task 3 原文](context/task3-review-input.txt)是该次工具输出的连续节选，保留原有待办状态，仅统一终端换行。其中已经写明：

> 同一event_id重发只保存一次；刷新后原预测仍在；迁移题更换参数，前端内容不含标准答案。

> 保留预测、实际run_id、答案、耗时与失败结果；其他会话数据不会混入；CSV能正确处理中文及换行。

> 所有正式作答追加记录，不让模型覆写。

这解释了为什么“有一个 CSV 下载按钮”仍不足以验收：Task 3 审查记录第 69 行指出，迁移作答 `30.5 Hz / correct` 附的是原运行 `70/110`，缺少实际题目 `80/110`、题干和 `question_id`，离线无法还原。还发现 GET 挂起时没有超时反馈。随后分别补出 `KeyError: 'question_id'` 和找不到 `alert` 的失败测试；`1c8897f` 修复后，导出分开保留 `question_params` 与 `run_params`，读取超时提供重试。详见 [失败、修复与复验](task3-learning.md)。

两次审查的派发调用分别位于主记录第 1401、1801 行，但存档中的 `message` 是不可读密文。本附件展示有明文证据、确实返回给审查模型的审查包／计划内容，**不声称已还原派发 message 本身或审查模型的全部输入**。

## 链 3：真实请求失败 → 收紧科学正文责任

[Task 4 完整链](task4-prompt-chain.md)仍保留三轮实际用户指令及 Codex 回复。[修复记录](task4-local-tutor.md)保留首轮十条 502、常量探针、JSON Schema 层级修复和后续复验，HTTP 200 只证明结构请求成功，科学内容另行核对。

[一条真实 C 模式输入与输出](context/task4-model-input-output.json)从 `2026-11-05-tutor-grounded-samples.json` 的 `/final_batch/rows/0` 提取，保留全部字段：模型 `context` 是原题 70/110、原预测 22 Hz、实测 40 Hz、理论说明及本次问题；模型原始 `raw` 返回 `focus`、`evidence` 和 `next_experiment`，应用 `reply.explanation` 则由程序根据已保存记录生成。模型该次建议 140 Hz 对照，保存的 `suggested_run` 如实显示奈奎斯特边界与退化采样；它与后续浏览器那次建议 200 Hz 是不同轮次，不能混成一次结果。

C 主流程的职责是：Qwen 选择观察重点、合法证据字段及可选对照参数；程序生成科学事实正文、检验证据所属运行和参数范围；学习者确认建议后，实验引擎才创建新运行。`validate_evidence` 检查运行和字段，不能自动证明任何自然语言都正确；C 的成功也不能包装为“模型自由推理正文全部正确”。

[B 模式真实错误样本](context/mode-b-error-sample.json)取自 `2026-11-06-synthetic-pilot.json` 的 `/cases/10`，保留原始文本：

> 当前实验频率 81Hz 低于奈奎斯特频率，发生混叠，理论折叠频率为 51Hz，实测主峰亦为 51Hz。

该运行采样率 132 Hz，奈奎斯特频率应为 66 Hz，因此“81Hz 低于奈奎斯特频率”是实际错误，不能修饰成正确答案后展示。B 按设计保留普通模型文本，不伪造结构化引用；这一个合成样本说明存在错误风险，不能推导 C 的教学效果优于 B。真人样本数为 0，学习效果仍为“未测”。
